# AI Harness 中核設計原則

本書は、AIエージェント開発とAIコーディングエージェント活用に共通する**規範的な正本**です。

Learning Guide、Reference、Profile、製品固有設定は、この原則を説明・具体化・強化できます。ただし、原則を弱めたり、製品都合で無効化したりできません。

## 適合ルール

- `MUST`は必須です。
- `SHOULD`は、合理的な理由を記録した場合だけ省略できます。
- `MAY`は任意です。
- Profile同士が競合した場合は、より制限の強い方を採用します。
- 原則の意味を変更する場合はCoreのメジャーバージョンを更新し、変更理由、移行影響、代替案を記録します。
- 数値、ツール名、製品設定は原則ではありません。代表タスクの実測と対象環境に合わせて変更します。

---

## CORE-01 モデルとエージェントを同一視しない

LLMはエージェントを構成する一部です。

```text
エージェント
= モデル
+ コンテキスト構築
+ ツール
+ 状態
+ 実行ループ
+ 権限
+ 検証
+ 可観測性
+ 評価
```

モデルを交換しても、ツール、権限、検証、状態管理が壊れていればシステムは信頼できません。評価対象はモデル単体ではなく、仕事を完了させるシステム全体でなければなりません。

## CORE-02 LLMは提案し、決定論的コードが許可する

LLMへ任せるのは、意図理解、候補生成、分類、計画案、検索語、説明文など、曖昧さを許容できる処理です。

型検証、認証・認可、金額上限、データ整合性、一意性、冪等性、操作可能範囲、監査は、通常コードまたは独立したPolicy層が担当します。

> **LLMは操作を提案できるが、実行権限を自分で付与してはならない。**

## CORE-03 成功を期待するのではなく、失敗を制御する

設計の中心に、次の問いを置きます。

```text
どこで失敗するか
→ どう検知するか
→ どう停止するか
→ どこまで戻すか
→ 誰へ引き継ぐか
→ 何を記録するか
```

誤ったツール選択、引数不正、同一失敗の反復、未完了終了、無限ループ、古い情報、重複副作用、予算超過、不確定な外部結果を通常の失敗モードとして扱います。

## CORE-04 作業ではなく成果を定義する

「ファイルを書いた」「APIを呼んだ」「テストを追加した」は作業です。

完了とは、要求された状態が成立し、既存挙動を壊しておらず、第三者が証拠で確認できる状態です。

Task Contractは作業手順だけでなく、観測可能なCompletion Criteriaを持たなければなりません。

## CORE-05 エージェントの自己申告より証拠を優先する

「修正しました」「正常に動くはずです」「問題ありません」は証拠ではありません。

テスト結果、API応答、差分、スクリーンショット、ログ、検証レポート、再現手順、監査イベントを、対象Versionへ結び付けて使用します。

説明文は証拠への索引として利用できますが、証拠そのものへ置き換えてはなりません。

## CORE-06 コンテキストは有限資源として配分する

コンテキストは保存場所ではなく、今回の判断に必要な作業領域です。

安全規則、目的、完了条件、現在状態、重要な制約を優先し、大量ログ、全文、古い会話、重複情報は外部Artifactへ退避します。圧縮後も、原要求、完了条件、未完了項目、重要判断、証拠参照を復元できるようにします。

## CORE-07 状態は会話の外にも保存する

長時間・複数セッションのタスクでは、計画、未完了項目、変更対象、検証結果、承認状態、予算使用量、再開位置を構造化して保存します。

会話要約だけを、業務データや現在状態の正本にしてはなりません。

## CORE-08 境界ごとに検証する

次の境界はすべてFailure Surfaceです。

- モデルからツール
- ツールからモデル
- 検索から回答
- 計画から実行
- 実行から完了判定
- エージェントからサブエージェント
- エージェントから人間承認
- WriterからReviewer
- Runtimeから外部System

後工程へ渡す前に、構造、必須項目、値域、出典、権限、鮮度、対象Version、データ分類を確認します。

## CORE-09 可観測性を後付けしない

少なくとも次を追跡できるようにします。

- 使用したモデル、設定、Policy Version
- モデルへ渡した情報の範囲
- 呼び出したツールと正規化済み引数
- 結果、再試行、状態遷移
- 検証と証拠
- 承認とAction Hash
- 時間、費用、停止理由
- 外部副作用と不確定結果

ログへ機密情報を無制限に保存しないことも可観測性設計の一部です。

## CORE-10 評価対象はモデルではなくシステム全体

評価対象には、モデル、Prompt、コンテキスト構築、検索、ツール定義、ツール実装、再試行、ルーティング、記憶、権限、完了判定、人間承認を含めます。

モデル比較だけで本番タスクの成功率、安全性、費用、保守性を判断してはなりません。

## CORE-11 不可逆な操作の直前に人間を置く

人間承認はすべてのStepへ一律に入れるのではなく、金銭、削除、外部送信、公開、権限変更、契約・法務、本番反映、個人情報利用など、判断価値が高い境界へ配置します。

承認対象は正規化した引数、対象Version、差分、送信先、件数・金額、不可逆性、Action Hash、Policy判定、Rollbackまたは補償方法へ結び付けます。承認後に対象が変わった場合は再承認します。

## CORE-12 複雑性は失敗が確認されてから追加する

最初からマルチエージェント、長期記憶、ベクトル検索、分散Queue、自己改善、複雑なWorkflow Engineを導入しません。

まず単一エージェントと最小ハーネスで代表タスクを実行し、観測された失敗へ対応する機能だけを追加します。

## CORE-13 改善されたモデルに合わせて制御を削除できるようにする

ハーネスは永続的に複雑化させるものではありません。

不要な再試行、Prompt規則、モデル固有の回避策、重複検証、使われていないToolやHookを削除できるよう、責任を分離し、Version管理します。

**削除可能性（Design for Deletion）**を設計品質の一部として扱います。

## CORE-14 制御の強制力を区別する

| 段階 | 目的 | 例 |
|---|---|---|
| 行動誘導 | Agentへ望ましい行動を伝える | Prompt、System Instruction、Skill、手順書 |
| 運用統制 | 通常フローで自動確認・停止する | Hook、Rule、Policy middleware、Validation Script、Approval UI |
| 独立した強制境界 | Agent自身が変更・無視できない場所で拒否する | OS、Container、Network Policy、Credential Scope、DB認可、Trusted CI、Protected Branch |

高リスク操作の安全性を行動誘導だけへ依存させません。越えてはならない境界は、Agentの出力や作業Workspaceから独立した層で強制します。

## コーディングエージェントへの適用命題

上記14原則から、AIコーディングエージェントの利用時には次が導かれます。

1. ベンダーのエージェントを、そのまま開発プロセスにしない。
2. Promptを安全境界として扱わない。
3. Agentの「完了しました」を採用条件にしない。
4. 安定した指示とTask固有情報を分離する。
5. Plan、Execute、Verifyを分ける。
6. 最小権限をTask単位で選ぶ。
7. 読取りは並列化できるが、書込みは隔離する。
8. ContextをRepositoryの代替にしない。
9. 同じ失敗を繰り返したらPromptだけでなくHarnessを改善する。
10. Harness自体をVersion管理、Review、Evalする。
11. 非対話の自動化ほどFail Closedを優先する。
12. 生成量ではなく、採用された変更を最適化する。

これらは別の理念ではなく、中核原則をRepository、Git、CI、権限へ適用したものです。
